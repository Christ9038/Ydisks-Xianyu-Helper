# 订单归属与一键同步修复计划

状态：已完成实现、真实账号验收及最终整轮门禁。2026-09-04 经用户确认按已发布版本的通用缺陷修复实施；本文中的真实两单只作为诊断样本，生产修复不依赖这些固定账号或订单号。未发布远端版本；外部数据库和真实新增交易的未验证范围见第 6 节。

## 1. 已证实的事实与证据边界

- 账号 `2222660684687` 的真实同步已取得并解析 12 个订单：10 个在本地属于该账号，另外 2 个属于 `203591535`，导致整批写入失败。
- 实际冲突订单是 `5127693841334047126`、`5127194991350001117`。两单的本地 buyer_id 均为 `203591535`，item_id 均为 `1075844330345`，且都在 2026-08-31 被软删除。
- `5127221415055001117` 不在本次 12 单列表中，商品也不同，不能随上述两单迁移。此前将其算作第三个本次冲突订单的结论撤回。
- 临时诊断文字“冲突订单”当时输出的是整个候选批次，而非 SQL 筛出的冲突集合；本计划的 2 单结论来自候选批次与真实归属的逐项交集。
- `isBuyerReviewedEvent` 不排除已识别的 buyer 角色，而付款、下单事件有此判断。此缺陷确实能让买家侧评价进入卖家自动化。
- `ExtractTaskFromWS` 使用接收账号创建 Task；`eventFactRecorder.record` 在匹配规则之前用 Task.AccountID 写入订单归属。因此无匹配规则也可能先写出错误归属。
- 没有首次写入审计，尚不能逐单证明上述两单最初必定由评价事件写入。应以脱敏真实单条事件回放补充证据，不能用包含多个会话的历史消息包推断单笔首次写入。
- `Orders.FindByIDs` 排除软删除记录，`upsertManyOrders` 的归属检查包含软删除记录；两者口径不同，导致旧错绑订单先被当成新增，再被数据库拒绝。
- 前端只展示 result.message；后端在 failed 大于零时仍拼接“同步完成”。真实任务 partial_failure=true，因此提示与实际结果不一致。

## 2. 必须保持的行为

1. 不新增登录、上线或重连自动同步。手动一键同步必须能恢复平台仍可查询的订单，并明确报告未完成部分。
2. 订单账号表示卖家账号；接收消息的账号、消息发送者、买家身份和卖家身份不得互相替代。本地 cookie_id 也不能一概视为平台 UID。
3. 普通 WS、手动录入、详情刷新和通用 Upsert 不获得跨账号迁移权限；order_id 主键与跨账号保护继续保留。
4. 同步及归属修复本身不触发发货、发卡、赠品或消息发送，不清空既有幂等记录来制造“新订单”。
5. 仅完整且可信的已售列表允许执行缺失订单软删除；任何未解决归属冲突或不完整分页均禁止该账号本轮缺失清理。
6. 保持状态防倒退、凭证变化检测、取消、账号隔离和旧请求不覆盖新请求的既有语义。

## 3. 实施方案

### A. 先固定回归样本，再修事件入口

- 增加 buyer/seller/无角色三类评价事件用例，覆盖 bizTag、订单链接、嵌套卡片中的现有角色来源。明确 buyer 事件在创建订单事实之前被拒绝。
- 将买家角色排除统一放到 WS 交易事件识别入口，覆盖付款、拍下、评价三种事件；保留已有函数的必要防御，不扩大至 scheduler/manual 的合法输入。
- 不用“我完成了评价”文案或 senderUserId 单独判断角色。现有卖家评价样本没有 role 字段，不能通过“必须 role=seller”把正常评价全部丢弃。
- 回放时核对角色与订单号是否来自同一交易卡片。多个矛盾角色或订单标识不得按 Go map 遍历顺序选一个；只有真实样本或确定性回归证明需修复的解析分支才调整，避免全量改写协议解析器。
- 补充从消息分发到事实记录的集成用例：买家副本先到、卖家副本先到、两者重复重放、无匹配规则，买家副本均不能新建或抢占订单，也不能生成自动化运行。
- 保持“先记录合法事实，再匹配规则”的行为，不能通过调整顺序让未配置规则的正常订单不再入库。

### B. 使用受约束的已售订单归属修正，而非只跳过冲突

- 为同步增加目的明确的非敏感归属查询，包含活跃与软删除订单，并返回旧账号、商品、买家、删除状态和并发版本；不改变普通列表/Get 的软删除可见性，也不读取其他账号的收货地址或凭证来判断归属。
- 应用服务按新建、正常更新、同账号恢复、可证实的买家侧错绑、未解决冲突分类。修复与恢复应单独计数，不伪装成新增。
- 自动修正仅限同时满足：旧、新账号都属于当前管理用户；当前已认证卖家会话的已售列表包含该订单；请求对应的平台身份与所选账号绑定一致；订单及商品事实一致；可靠买家身份表明旧账号是买家而不是另一个卖家。
- 不能仅凭 cookie_id 字符串等于 buyer_id、同一个商品号、同一管理用户、软删除状态或“接口返回过”就迁移。必要身份核验由平台/账号适配边界提供最小非敏感结果，不在 HTTP 层处理凭证。
- 只有同步应用服务可调用专用归属修正事务能力；不能给通用 Upsert 增加任意 force=true 开关，不能删除冲突保护或改变为按 cookie_id+order_id 复制订单。
- 事务提交时重查旧归属、版本和同用户所有权，以期望旧账号及版本作条件更新；归属修正、必要的账户相关字段处理、已售事实合并及恢复软删除在同一事务完成。并发变化时重读并有界重试，不能覆盖新的归属。
- 外部身份/订单核验在事务外进行；提交前复核凭证绑定或代次。不得在数据库锁或凭证锁内等待网络。
- 成功确认的订单可以独立于未解决的业务冲突提交；未解决冲突按订单号报告并保留原数据，不能作为成功。底层数据库异常仍回滚当前事务，不能吞掉错误后继续报完成。

### C. 历史数据、关联记录与并发保护

- 所有已发布用户升级后通过一键同步自动发现并核验历史候选，不要求手工定位订单、提交日志或重新登录旧买家。修复在事务内记录旧非敏感字段，支持审计与失败回滚；证据不足保留原数据并在同步结果报告。真实环境验收前额外建立一致性备份，本机样本第三单不随本次两单迁移。
- 核对 automation_runs、automation_pending_tasks、发货/卡密使用记录、通知待发记录及订单上的 chat_id、system_shipped、评价/催评时间。不能把买家侧会话和发送状态直接当作卖家侧状态使用。
- 已确认完成的历史动作保留原执行账号和审计含义，不迁移运行账号、删除发货记录或重置幂等键。仅在证实是错误买家上下文且不存在执行副作用的情况下修正相关字段。
- 如存在执行中、待恢复或结果不确定的外部动作，暂停该订单自动修正并报告复核原因；不得在运行中直接换归属，导致旧 worker 继续发送。
- 旧账号延迟到达的 WS 事件及恢复任务必须再次经过归属保护；重复同步不能把订单迁回买家账号，也不能重复产生外部动作。
- 自动化运行领取、延期写入和动作领取按“账号 → 订单 → 运行/延期”顺序在短事务内再次核对归属；准备阶段成功不等于仍有执行权，外部动作只能在领取事务提交后执行。
- 保留工作区已有的规则物理删除行为；独立的 `order_automation_guards` 仅保存订单、账号和时间，不随规则级联删除。升级时回填现有运行，之后创建运行时原子登记，以免删除规则后丢失自动修复所需的执行痕迹。升级前已经被彻底删除的历史执行记录无法从空数据中重建，不宣称可以追溯恢复。
- 普通批量写入目前是“先查归属，再 UPSERT”；SQL 更新分支本身合并 cookie_id。必须补充并发插入/归属变更用例，证明写入时保护有效；必要时增加数据库原子条件或锁，不得只依赖进程内锁和前置 SELECT。

### D. 完整性与真实反馈

- 为已售抓取结果显式记录完整性。达到分页上限但 nextPage=true、空解析页但平台仍有后页、页请求失败、取消和无效必要结构都不能当作完整成功。
- 保持合法空列表兼容；不能因 totalCount 与去重数的简单差值就判失败，因为分页期间平台订单可能变化。以真实协议与分页终止信号定义完整性，异常场景保留本地订单并报原因。
- 缺失软删除仅在完整抓取、归属处理和保存都满足条件时执行；业务冲突允许其他订单同步，但阻止该账号本轮缺失软删除。
- 后端结果分别表达新增、更新、恢复/修正、失败及未完成原因；仅全部成功时显示“同步完成”。失败项的账号/订单只对有权限用户可见，不暴露跨管理用户的旧归属。
- 前端消费 partial_failure 与逐项结果，明确展示失败账号/订单及原因。保留 generation、取消和筛选切换的旧响应隔离。
- 同账号并发发现请求使用服务拥有的代次窗口；最新请求完成、失败或取消都不重新授权旧快照提交。不同账号互不阻塞，所有调用返回后释放窗口，不持内存互斥锁等待网络；凭证已变化的旧会话错误不再触发恢复。
- 尽量沿用已有任务接口；若需新增计数字段，同步修改 OpenAPI、生成类型、服务端具名 DTO、feature adapter 和真实 handler 契约测试，不手改生成文件。

## 4. 验收条件

| 场景 | 必须结果 |
| --- | --- |
| 买家先收到付款、拍下或评价卡片 | 不创建卖家订单事实，不创建发货/赠品任务 |
| 卖家有角色/合法无角色评价卡片 | 保持原有正常识别及规则匹配 |
| 同一交易买卖副本乱序、重复、并发 | 最终只归属正确卖家，外部动作至多按既有幂等规则执行 |
| 10 单正常 + 2 单已证实软删除错绑 | 12 单均归正确卖家；2 单恢复且归属修正，原 10 单不丢失 |
| 再点一键同步或重启后再同步 | 0 次新增归属修正，无重复订单、重复发卡或状态倒退 |
| 跨管理用户或证据不足的冲突 | 不迁移、不泄露旧账号数据；正常订单可提交，冲突明确失败 |
| buyer_id/商品身份矛盾、旧账号缺失 | 不根据字符串或单一字段强行归属 |
| 分页失败、上限未完、异常空页、取消 | 不误报完整成功，不对缺失订单做软删除 |
| 凭证切换、并发 WS/同步/任务恢复 | 旧结果不能覆盖新归属；事务失败可回滚 |
| 错绑订单有待执行或结果不确定的动作 | 不自动迁移后重发，保留记录并报告需复核 |
| 前端全失败、部分失败、切换筛选、旧任务晚到 | 提示与统计一致，旧任务不覆盖当前列表或提示 |

验证顺序：先增加能暴露现状的聚焦回归，再完成窄范围修复并复测；执行仓库要求的 make check、make comments、架构与 API 门禁、Go/前端覆盖率及嵌入前端构建。数据库变更以 SQLite、可用的 MySQL/PostgreSQL 验证事务和并发条件；涉及浏览器的本地回归按仓库要求执行 make cover-browser。记录 RUN_BROWSER_INTEGRATION、实际覆盖率及外部账号例外，不能以现有测试通过代替新增场景验证。

真实账号验收先在隔离数据库副本上验证数据修正，再在备份和修复预览基础上验证当前两单的一键同步恢复、账号筛选及重复同步。断线期间产生新单、重新登录后人工同步的端到端场景需真实新增订单或受控消息/平台夹具支持；未执行不得宣称通过，也不为测试擅自下单或触发真实发货。
